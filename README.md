## 3. Methodology for Auditing API Lies

To audit `https://solve.ivy.homes`, we treated the running API as the ground truth and systematically tested every claim made in `API_REFERENCE.md`:

### 1. Reverse-Engineering Auth & Headers
- **Documented**: Documentation claimed requests should append `?api_key=IVY26-...` as a query parameter, and user sessions last 24 hours (`expires_in: 86400`) without a refresh endpoint.
- **Audit**: Query parameters resulted in HTTP 401: `"send your key in the X-API-Key request header, not as a query parameter"`. Furthermore, tokens expire in **900 seconds (15 minutes)**, response keys are named `access_token` and `refresh_token`, and an explicit refresh route exists at `POST /auth/refresh`.
- **Logout**: `POST /auth/logout` returns `{"ok": true, "note": "tokens are stateless; discard them client side"}`. The server does not invalidate JWTs server-side; client-side purging is required.

### 2. Uncovering Real Pagination Mechanics
- **Documented**: Documentation claimed endpoints use 1-indexed `page` (default 1) and `limit` (max 200), and that `total` is the exact number of matching records.
- **Audit**: 
  1. The `page` parameter is completely ignored by the server. Only 0-indexed `offset` advances through the records.
  2. The server hard-caps `limit` at **50**.
  3. The `total` field is truncated (`total: 4659`). However, repeatedly incrementing `offset` until `has_more == false` retrieved **5,100 unique listings**, **2,100 rentals**, and **590 projects**.

### 3. Systematic Corruption Auditing (44 Records)
We ran automated dimensional boundary checks across all 5,100 listings:
- **Carpet vs. Super built-up**: Exactly 11 records had `carpet_area > super_built_up_area` (e.g. `DWE-5002147`: 1,951 sqft carpet vs. 1,149 sqft super built).
- **Floor vs. Total floors**: Exactly 11 records had `floor > total_floors` (e.g. `100-5000050`: floor 18 in a 10-storey building).
- **Impossible Prices**: Exactly 11 records had negative prices (e.g. `100-5002758`: -₹6,46,40,000).
- **Geographic Bounds**: Exactly 11 records had coordinates outside the Mumbai bounding box (`18.8°N - 19.4°N, 72.7°E - 73.2°E`). Inspecting them revealed that latitude and longitude were swapped (e.g. `lat: 72.77894, lon: 18.96835`, placing the property into the Arabian Sea).
- Each category contained **exactly 11 records** with zero overlap, confirming deliberate synthetic corruption totaling **44 IDs**.

### 4. Telemarketing / Lead-Gen Fraud Identification (313 Records)
- Analyzing the distribution of `posted_by_contact` phone numbers across all 5,100 listings revealed 856 unique phone numbers.
- Genuine owners and agents posted between 1 and 14 listings.
- There was a noticeable gap between 14 and 19 listings, followed by **exactly 10 phone numbers** that each posted between 19 and 38 listings (top number: `+912007133812` with 38 listings).
- These 10 phone numbers posted identical flats across wildly different localities under different agent names, creating **313 fake lead-generation listings**.

### 5. Multi-Portal De-duplication (5,079 Unique Properties)
- Grouping listings by physical property signature `(apartment_name, locality, bedroom, floor, carpet_area)` revealed **21 duplicate pairs** (42 listings total).
- For example, `ZER-5004905` (ZeroBroker) and `MAG-5002375` (MagicHomes) both describe the exact same 3 BHK flat on floor 7 (1,156 sqft) in Rohan Park, Thane West, with coordinates differing by only 25 meters due to aggregator GPS jitter.
- Deduplicating these pairs results in $5100 - 21 = \mathbf{5079}$ distinct properties.

### 6. Project Total Listings Inconsistency (446 Discrepancies)
- `API_REFERENCE.md` claimed `total_listings` in `/v1/projects` always agrees with real-time active listings with matching `project_id`.
- Comparing reported project totals against actual listings in `/v1/listings` revealed that **446 out of 590 projects** have mismatched listing counts (e.g. `P50001` reports 18, but only 6 listings reference it).
- Furthermore, `GET /v1/listings?project_id=...` quietly ignores the parameter and returns the full dataset.

### 7. Missing Endpoints

## 4. Negative Hypotheses (What Was Checked That Turned Out Fine)

Forming hypotheses and proving them false was critical to maintaining high precision:

### Hypothesis 1: Coordinates were systematically swapped across all Mumbai records
- **Hypothesis**: After noticing that `MAG-5002818` had latitude 72.77894 and longitude 18.96835, we hypothesized that the entire database used swapped (long, lat) GeoJSON conventions.
- **Verification**: We checked the coordinate bounds of all 5,100 listings against Mumbai's geographic bounding box (18.8°N - 19.4°N, 72.7°E - 73.2°E). Exactly 5,089 records had standard (latitude, longitude) coordinates inside Mumbai; only 11 specific records were corrupted with swapped coordinates.

### Hypothesis 2: Rental deposits were stored in Thousands rather than full Rupees
- **Hypothesis**: Because rental prices in Mumbai often require deposits of 5 to 10 months' rent, we checked whether deposit values like `250000` were scaled or recorded in thousands.
- **Verification**: Computing the ratio of `deposit / price` across all 2,100 rental records revealed that the median ratio is 6.5x monthly rent (consistent with Mumbai market practices). Deposits are stored as full INR values.

### Hypothesis 3: Carpet areas were recorded in Square Meters
- **Hypothesis**: We hypothesized that carpet areas were stored in square meters while super built-up was in square feet.
- **Verification**: Comparing carpet area values against typical bedroom configurations (1 BHK: 400–650 sqft; 2 BHK: 650–1,100 sqft; 3 BHK: 1,000–1,800 sqft) showed standard square footage values matching Indian real estate conventions.

### Hypothesis 4: Timestamps had timezone skew or missing offsets
- **Hypothesis**: We checked whether `posted_at` timestamps in `/v1/listings` lacked timezone offsets and were being misread in UTC instead of IST.
- **Verification**: All 5,100 `posted_at` timestamps strictly adhered to ISO 8601 with explicit `Z` UTC suffixes. Only the `/health` endpoint exhibited timezone offset discrepancy (`+05:30`).

## 5. Frontend Architecture & Resiliency Patterns

Built with Next.js 15 (App Router), TypeScript, and Tailwind CSS:

1. **Authentication & Session Longevity**:
   - `POST /auth/login` connects with `X-API-Key` and saves JWT to `localStorage` and `cookies`.
   - Client-side token refresher automatically intercepts expiring tokens (under 60s remaining) and calls `POST /auth/refresh` or re-authenticates silently.
   - Quick one-click demo switcher between `demo1`, `demo2`, and `demo3` with password `acb9e1f812`.
2. **Client-Side Filtering Fallback**:
   - Because the server ignores `furnishing`, `project_id`, and descending `sort_by`, the client executes filter predicates in-memory on the loaded dataset (`lib/api.ts`).
3. **Persistent Favourites**:
   - Since `/v1/favourites` returns 404, favourites are saved in `localStorage` namespaced by user email (`ivy_favs_${email}`), ensuring complete isolation between demo users and persistence across page reloads.
4. **Similar Listings**:
   - Because `/v1/listings/{id}/similar` returns 404, recommendations are computed on the client matching the same locality, bedroom count, and ±15% price band.
5. **Insights Dashboard (`/insights`)**:
   - Renders live market aggregates (median price, price/sqft, locality breakdown).
   - Visual audit panels for corrupt listings, lead-gen clusters, and project count discrepancies.
   - Searchable and expandable catalog of all 18 API discrepancy findings with evidence IDs.
